이 리포트는 2026-07-29 시점의 Valve 소스(v0.3.9, e3f9e8f)를 그대로 읽어 기능 단위로 정리한 것이다. 각 기능마다 ① 인포그래픽 ② 동작 설명 ③ 폴백·예외 처리를 함께 싣는다. 폴백을 강조하는 이유는 단순하다 — Valve 가 다루는 실패는 대부분 터지는 실패가 아니라 조용히 틀린 데이터가 나가는 실패이고, 그걸 막는 장치들이 이 시스템의 실질적인 본체이기 때문이다.

02Lake API 어댑터 backend/core/lake_api.py
사내 DataLake 의 query(params, custom_col, user) 하나를 감싸는 얇은 어댑터. 인증 정보는 user_name 하나뿐이며(키·토큰 없음), 그 위에 rate limit · timeout · 재시도 · 타입 정규화 4가지 보증을 얹는다.

Mock ↔ Real 전환

기본값은 mock이다. 설정 탭에서 lake_api.mode = real 로 바꾸고 module 에 패키지.모듈:함수 를 적으면 importlib 가 그 함수를 불러 쓴다. 사내 getData 는 keyword 시그니처라 그대로 꽂히지 않으므로 얇은 어댑터를 하나 둔다.

mycorp/valve_adapter.py → 설정 탭 module: mycorp.valve_adapter:query from bigdataquery import getData def query(params, custom_col, user): if custom_col: # 빈 리스트면 전체 컬럼 (인자 자체를 뺀다) return getData(params, custom_columns=custom_col, user_name=user) return getData(params, user_name=user)
인증은 user_name 하나뿐이다. v0.3.9 에서 쓰지도 않던 lake_api.api_key 를 설정·UI·매뉴얼에서 걷어냈다(구버전 설치에 남은 값은 조회 응답에서 걸러지고 저장 시 사라진다). 다시 넣지 말 것 — 없는 인증 필드는 "왜 안 되지"의 시간을 만든다.

03Probe-First 2단계 계획 backend/core/planner.py
하루치를 통째로 쏘기 전에 1시간 샘플로 크기와 shard 분포를 재고, 그 추정으로 chunk 를 나눈다. 측정 결과는 (제품::소스) 키로 7일 캐시돼 한 번 재면 일주일 재사용한다.

동작

  • sample_window — date T00:00 ~ +1h 을 shard 키 1개 컬럼만 받아 조회하고 행 수에 24/hours 를 곱해 하루를 추정한다. 동시에 그 시간대에 등장한 shard(예: root_lot_id) unique 를 최대 1000개까지 담는다.
  • projection — 하루 전체를 조회하되 shard 컬럼 1~2개 + time 만 받는다. 정확하지만 비싸다.
  • none — probe 를 아예 걸지 않는다. 소스·제품 단위 probe_skip: true 로도 같은 경로가 된다 (probe 가 상습 실패하는 소스용).

22알려진 한계 · 다음 단계 솔직한 현재 상태
1. 파이프라인 raw 는 아직 mock 합성이다.
feature_pipeline._run_raw_unit 은 lake_api 를 호출하지 않고 결정적 합성 데이터를 만든다. 실 어댑터를 쓰는 것은 모니터 탭의 제품 백필 경로(probe → chunk → executor)다. 즉 lake_api.mode: real 로 바꿔도 파이프라인 5단계는 여전히 합성 데이터로 돈다. VERSION.json 의 "다음 — 실사내 API 연결"이 이 작업이며, 붙는 지점은 _run_raw_unit 의 생성기 자리 하나다 (컬럼·파티션·필터 규약은 이미 실 데이터 기준으로 맞춰져 있다).
2. _SUCCESS 마커가 없다.
개별 파일은 원자적으로 쓰이지만(put_atomic), 파티션 폴더가 반쯤 채워진 순간에 flow 가 읽으면 일부 파일만 보게 되는 이론적 race 가 남아 있다. 실무 영향은 작지만(flow 쪽이 관대하게 fallback) 정합성 보강 여지로 남는다. docs/flow_integration.md §6
3. 백필 경로의 S3 key prefix. executor 는 {SOURCE}/{PRODUCT}/date=…/part-0.parquet 로 올린다. flow 의 규약은 1.RAWDATA_DB_{SOURCE}/… 이므로, 한 버킷을 직접 물릴 때는 prefix 한 줄 정렬이 필요하다 (s3.prefix 설정 또는 key 규칙 변경). docs/flow_integration.md §3 Option A/B — 다만 이 문서는 2026-04-24 기준이라 현재 파이프라인/전송 항목 엔진 구조와는 일부 어긋난다.
4. 알람 outbox 는 "폴더를 올려주는 누군가"가 필요하다. Valve 는 s3_outbox/valve-alerts/ 를 항상 최신으로 유지하지만, 실제 업로드는 ① s3_jobs 의 up_valve_alerts 항목(자동 시드, 10분 sync) 또는 ② 외부 aws s3 sync 중 하나가 담당한다. 둘 다 꺼져 있으면 flow 는 알람을 못 본다.
5. 검증 범위. python -m pytest tests -q 기준 187개가 모두 mock 경로를 탄다. 실 어댑터·실 S3 는 테스트 대상이 아니다. 시계에 의존하는 기본값(실행 금지 시간대 등)은 pipe fixture 에서 꺼야 새벽에 도는 테스트가 깨지지 않는다.
